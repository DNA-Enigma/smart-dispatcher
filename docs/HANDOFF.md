## 6. 我这边的工作标准（便于你验收）

这几条不是偏好，是这个项目一路踩出来的。**用它们来验收我的产出**：

1. **每条断言都要有机械证据。** "接缝成立"→ 哈希断言；"契约一致"→ 一条测试；
   "机制有效"→ 一次真实对照实验。没有证据的结论我不写进报告。
2. **反例必须因该失败的那一条而失败。** 只测"拒绝"不测"放行"的测试，
   抓不到"约束过宽把所有合法输入都拒了"这类 bug——我在这上面栽过两次。
3. **静默失效比报错更糟。** 死配置、恒真的兜底判空、写坏的谓词、
   "看起来在跑实际永不触发"的监控——这几类我都遇到过，都会让系统安静地做错事。
4. **契约与配置各写一份就一定会分叉。** 要么一处是真源，要么自动化检查盯着。
   人工核对的清单一定会漏。
5. **不猜领域。** 遇到"这个字段该叫什么"，我去问，不替你定。

**2026-10-07 追加：这一轮报来的三个缺口已处理**（消费端口头反馈，无书面报告）

| 缺口 | 处置 |
|---|---|
| taxonomy 缺 `bookkeeping.categorize_merchants`（P1-c 批量归类） | 补词表项 + handler 能力 + 批量工具 `categorize_merchants`。只补词表项会更糟：评估器会归到这个类型、画像给出这个能力名，却没有任何 handler 认领 → 守卫推不出 handler → 降级 → 422 |
| `direct_llm` 路径报 502 `handler_error`（问账、归类） | **契约里声明了三种执行路径，只有两种被执行过。** `path=direct_llm` 的请求落进拆解器后被套成"单步工具调用"，产出 `handler=""`、`tool=None` 的节点 → 执行器找不到实现 → 502。补上第三种执行器（`stages/direct.py`）。**注意：它不该是 `handlers/` 下的一个 handler**——schema 的 allOf 规定该路径 handler 必须为 null，守卫也会主动清空，挂上去会在守卫那一跳被抹掉 |
| 日程歧义时直接建日程、没走确认（P1-e 后半） | 见第 7 节，三处接线 |

顺带修掉一处**静默失效**：`clarify` 恢复时 `node_outputs` 从来没有落过盘，
于是"答复后从断点继续、已完成节点的产出保留"这句话一直是**假的**——上游节点会从头
重跑（白花钱，而且可能产出与用户刚确认过的那份不同的结果）。现在暂停时把它落盘，
并有测试用"模型调用次数不变"钉住。

三项都有反例检验：把对应的那一处接线各去掉一次，测试因**该失败的那一条**而红。

那份报告的形式很好用，值得作为标准：

- 每条都有**复现命令**与**证据**（不是读代码推测的）
- 按优先级排序（P0/P1/P2）
- 末尾附"**已确认没问题的部分**"——免得一长串问题让人以为整条链都是坏的

其中三条是我的真 bug，值得记住类型：

1. **判定加错了地方** —— 模板的 `applies_when` 写着"需要图像"，命中判定却不看模态。
   修法是从模板自己的绑定推导需求，而不是加一条领域规则。
2. **开关没传到该传的地方** —— 三个阶段都传了"关掉深度思考"，节点执行那条路径没传。
   后果是抽取跑了 31.7 秒（超时 20 秒），正确结果被整单丢掉。
3. **死配置** —— `node_defaults` 声明着、配置着，**没有任何代码读它**。
